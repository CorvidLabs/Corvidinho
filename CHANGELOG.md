# Changelog

## 0.0.34

### Knows everyone (M1)

- **The owner declares who's who, and Corvidinho recognises each declared person on Discord and GitHub by stable ids** — [#271](https://github.com/CorvidLabs/Corvidinho/pull/271) (IDENTITY-13, IDENTITY-14, IDENTITY-6, IDENTITY-7, ADMIN-3.a; REQ-discord-036, REQ-watch-036, REQ-discord-043, REQ-discord-446): Corvidinho knew only the configured owner; everyone else was a bare Discord id or GitHub login. The allowlist file the process loaded (the one `[owner]` comes from; a `people` object in a JSON file) now takes `[people.<id>]` sections with `display`, `nicknames`, `discord_ids`, `github_logins` and `github_ids` (singular spellings are read too). A person id is a lowercase slug of up to 32 letters, digits, `-` or `_`; `owner` is reserved. People are matched only on Discord user ids, GitHub numeric ids and GitHub logins, never on a display name or nickname; a login match is dropped when GitHub reports a numeric id and the person declared other `github_ids` (with no `github_ids` declared, the login alone matches), and an id declared for two people matches nobody. An entry with any unreadable value is skipped whole and reported by person id and key, never by account id. The list is re-read on every use, so edits apply without a restart. The configured owner is always a person (the declared holder of the owner's Discord id, else a built-in `owner` entry). On Discord, chat, button-pick resumes, `/session start` and `/work` add `declared_person`, the declared `display_name` (which now wins over the Discord name), `nicknames` and `github` to the IDENTITY-4 block, matched on the acting Discord id only; once anyone is declared, an undeclared speaker other than the owner is marked `declared_person: none`, and with nobody declared (or for an owner not declared under `[people]`) #271 leaves the block as it was (the SAFE-11 name cleaning and `name_clash` line from #295 below still apply). On GitHub, WATCH events now carry the commenter's numeric id, and the run prompt carries a `[Corvidinho acting GitHub user …]` block (after any #292 memory blocks) for a declared commenter and for the `[owner]` login (`role: owner`, which still gets no ADMIN tools in a GitHub run); once anyone is declared, an undeclared commenter's block says `declared_person: none`. New owner-only `/admin people list|add|link|unlink|remove` (still nine top-level slash commands) is the only writer besides the VM file: each change writes a SAFE-5 `admin-people-<op>` row (`started` before the atomic write, then `ok` / `error`; refusals and non-owners `denied`), and with no audit trail it is refused and nothing is written. A re-read safety net refuses any rewrite that would touch allow/deny lists, `[owner]`, another person or another section, TOML edits keep the person's header, comments and unread keys, and linking an id already held by someone else (including the `[owner]` login) is refused. `/admin config show` counts declared people. A WATCH process started without an allowlist file needs a restart to see one created later.
- **Owner, team and community roles gate every tool, re-checked in the tool layer on every call** — [#285](https://github.com/CorvidLabs/Corvidinho/pull/285) (IDENTITY-8, IDENTITY-9, IDENTITY-10, IDENTITY-11, IDENTITY-12, ADMIN-3.b, ROLES-CHAT-8.a; REQ-plugins-065, REQ-plugins-066, REQ-agent-065, REQ-discord-065, REQ-discord-043, REQ-discord-088, REQ-agent-501): the tool gate had two tiers, ADMIN (the owner) and everyone else. Each `[people.<id>]` entry now takes `role = "team"` or `role = "community"`; no `role` key is community, the configured owner is always owner, `role = "owner"` on anyone else grants nothing (community, with a reported problem), and a list or unknown value makes the entry unreadable and skipped whole. The role is resolved again at every tool call from the owner config and the people list read fresh, matched on the Discord id only; `runPlugin` and the task-run catalog share one rule, and an allowlist file that cannot be read or parsed (any error while resolving) reads as community. The Discord spawn stamps `CORVIDINHO_ACTING_ROLE` (and `CORVIDINHO_ACTING_WORK_TASK=1` for `/work`) as a per-surface cap that can only lower the role; chat, button picks, `/session start` and `/work` spawn with the speaker's role, while WATCH, schedules and `delegate` / `council` workers are community. Owner is today's ADMIN. Team gets the read tools, `github-issue-comment` and `github-pr-review` (still behind SAFE-1, only on GITHUB-6-allowlisted repos, and a team review with `--event APPROVE` or `REQUEST_CHANGES` is refused exit 2, `Denied: github-pr-review --event … is not allowed for your role (IDENTITY-10: team reviews post as COMMENT).`), and `files-write` / `files-edit` only in their own `/work` run (SAFE-2 applies and secret-looking paths are refused); their `/work` opens the draft PR like the owner's, with the role checked again after the run so a member demoted meanwhile gets no PR. Memory store and recall stay their own; forget and override stay owner-only; no shell, runners, git writes, other GitHub writes, Discord posts, `web-fetch`, `delegate` or `council`. Community keeps today's non-ADMIN catalog with no mutating tool. Team reads work on allowlisted or confirmed-public repos, team writes only on allowlisted ones, community writes are refused, and deny lists still come first. Two new read-only tools serve ROLES-CHAT-8.a behind the acting role's repo gate: `github-docs-read` (the README by default, a root `STATUS*` / `CHANGELOG*` file, or anything under `docs/`, where a directory lists up to 200 entries; any other path is refused before GitHub is called; text scrubbed, capped at 64 KiB and labelled untrusted; secret-looking doc paths are refused and hidden for every non-owner) and `github-milestone-list`. New owner-only `/admin people role person:<id> role:<team|community>` writes the SAFE-5 `admin-people-role` row before the atomic write, fails closed without an audit trail, and refuses the owner role, unknown roles, undeclared people and the owner's own person; `/admin people list` shows each role and `/admin config show` counts them. With no role stamp (the local CLI, older callers) the old ADMIN bit behaves exactly as before.
- **Each declared person has one memory profile, each project has shared memory, private notes stay private, and anyone can ask to be forgotten on an owner Approve/Deny card** — [#291](https://github.com/CorvidLabs/Corvidinho/pull/291) (MEMORY-5, MEMORY-6, MEMORY-7, MEMORY-ACL-6; REQ-discord-101, REQ-plugins-101, REQ-agent-101, REQ-discord-021, REQ-plugins-010): memory was keyed only by Discord id. A declared person's memory is now one profile, scope `person:<id>`, reached from every Discord id linked to them; rows stored under those ids before they were declared are still read, and undeclared users keep their Discord-id scope. New categories `project`, `preference`, `decision`, `ask`, `approval` and `private`; the new `memory-profile` shows the person's role (from the people list), projects, preferences and history newest first, and only counts private notes. Project memory, scope `project:<key>`, is keyed by the `origin` remote's owner/repo, lowercased with any URL credentials dropped (without an `origin`, the main checkout's real path, so every talk worktree shares it); the owner, team and the local CLI use it with `memory-store --project` / `memory-recall --project`, owner and team chat, button-pick and `/work` runs get it as a second prompt block, and community, schedules and workers cannot read or write it (WATCH reads it only as below). Only the owner may read another person's memory with `--person`; anyone else gets a plain `not authorized` whether or not that person exists. Private notes (`--category private`) are never injected into a prompt and come back only when that person or the owner asks for them with `memory-recall --category private` in a Discord conversation (a run with a reply channel: chat, button picks, `/session start`, `/work`), never in a schedule or other run (`refused: private notes are shown only in a conversation with that person or the owner, never in a schedule or other run (MEMORY-7)`). The new `memory-forget-me` records the acting person's ask (audited, one open ask per person, deletes nothing; refused when no owner is configured). The bridge DMs the owner an Approve/Deny card on every scheduler tick and right after each chat message, naming who asked, how many memories Approve would delete (never their content), what is kept and when it lapses. Only the owner's press counts, re-checked at press time. Approve writes the SAFE-5 `memory-forget-approve` `started` row first (no row, nothing deleted), then one transaction closes the ask and deletes every memory row and stored session turn of that person, and the running bridge drops the session threads it holds for them; the press is answered first, then the asker is told by DM (or in the allowlisted conversation they asked in if the DM fails, retried for about a day). Deny, no answer within 24 h, or a late press is a no and deletes nothing. Kept: the people-list entry, project memory, what others stored, schedules, `/work` records, the sessions themselves, the ask row and the audit trail. Asks live in the new `forget_requests` table (added by the v12 migration; with #296 the release ships schema v13; ids, status and times only, nothing to scrub). No new config key, env var or slash command.

On GitHub, project memory is read-only for everyone, and `--person`, private notes and `memory-forget-me` are refused (threads are public). `memory-recall --query` is now a ranked search: question words dropped, light stemming, idf-weighted term hits, key hits counted double, a whole-query bonus, times a recency weight with a 30-day half-life that never drops below 3/4, over at most 500 candidates (no FTS table, no schema change). A loop guard runs when a final reply says it doesn't know and the person's own or the project's memory was not searched in that attempt: it runs only the missing `memory-recall --query` / `--project --query` itself through the normal plugin gates, keeps the reply when nothing is found (no extra model call), and otherwise gives the facts back to the model once without using a tool round. Recall results are now ordered by relevance first.

- **A nightly SQLite backup goes to a directory the owner sets, a weekly restore test checks it, and `corvidinho backup restore` puts one back** — [#281](https://github.com/CorvidLabs/Corvidinho/pull/281) (OPS-1, OPS-2; REQ-cli-680, REQ-discord-680): there was no backup. New optional `CORVIDINHO_BACKUP_DIR` must be an absolute local directory outside any git work tree (a symlink into one is refused too); unset means no backup, as before. From the existing scheduler tick of the bridge and `corvidinho daemon`, at the first tick at or after 03:00 local time, the night is claimed in SQLite (a bridge and a daemon on one data dir back up once, and the daemon backs up even on a tick whose allowlist file fails to load); `VACUUM INTO` writes a consistent copy under umask 077, re-scrubbed first if the scrub rules tightened, which is checked (integrity_check, schema version, tables, row counts), fsynced and renamed to `corvidinho-<UTC>Z.db` (mode 0600). The newest 7 are kept; other files are never touched except a crashed run's `.corvidinho-*.db.tmp` older than an hour. Weekly, and every night while it is failing, the newest snapshot is restored into a temp dir with the restore code, checked against the row counts recorded when it was taken, and deleted. Every run is logged (daemon JSON events `backup.ok` / `backup.failed` / `restore_test.ok` / `restore_test.failed` / `restore_test.skipped`, bridge `[backup] <event> {…}` lines); the first failure of a streak records an owner notice that the bridge's next tick posts once to the `/announce` channel pinging only the owner, as fixed text (`⚠️ The nightly backup failed (…)` / `⚠️ The restore test failed (…)`, no host path or error), handed back and retried every tick when the post does not go out (a bridge stopping mid-post waits 3 s, then hands it back); while it cannot post, the bridge logs `[backup] backup.owner_not_told {…}` (or `restore_test.owner_not_told`) once, then `….owner_told` when the notice goes out. A job whose process died is recorded as that job's failure (`interrupted: true`) and told. New `corvidinho backup list` and `corvidinho backup restore <snapshot> <target> [--force]` (exit 1, `restore refused: …`; both read `CORVIDINHO_BACKUP_DIR` from the shell that runs them and exit 1 with `CORVIDINHO_BACKUP_DIR is not set …` when it is unset, and `<snapshot>` is a file name from `backup list`, not a path): a target any process holds open (a `/proc` fd scan, plus a live `daemon.lock` for `corvidinho.db`) is refused even with `--force`, any other existing target needs `--force`, and a snapshot with a schema newer than the build is refused. `corvidinho doctor` gains a `backup` line, `[warn]` when off, unusable, failing or when no `/announce` channel is set, never failing doctor. State lives in `schema_meta` `ops_*` keys; no table or schema version.

The model is told it can attach (never to say it can't) only when the tool is offered and the run has a conversation channel. Images are not scrubbed or EXIF-stripped, and one file goes per call.

- **Long chats are condensed at about 80% of the model's window with the task and latest instruction kept word for word, a conversation is kept 30 days so a reply after the TTL resumes it, and WATCH follow-ups replay the issue or PR thread** — [#296](https://github.com/CorvidLabs/Corvidinho/pull/296) (SESSION-5, SESSION-6, SESSION-3.a, AGENT-6.a; REQ-discord-472, REQ-watch-472, REQ-discord-072, REQ-discord-019, REQ-watch-037): a continued Discord session replayed at most 6000 characters of earlier turns (each clipped at 1500, the middle dropped as `(N earlier turns omitted)`), its turns were deleted when it ended or idled out, so a reply to one of its answers after the soft TTL was ignored (an @mention started fresh with nothing replayed), and a WATCH follow-up carried only the newest event. When the conversation part of a prompt (the replayed block plus the new message) reaches 80% of the window, the oldest turns are now folded into a summary one at a time until it fits, with no model call: each becomes one point of its own opening words (`- Human: …` / `- You (Corvidinho): …`, up to 160 characters) under `Condensed summary of earlier turns (the task, the latest instruction and the newest turns are word for word):`, and the summary stays within a third of the budget (500 to 6000 characters), its older points shortened to 80 characters and then counted as `(N earlier points left out)`. The session's opening human turn (the task) and its newest human turn (the latest instruction) are never folded, and the new message is never touched. The window is the new optional `CORVIDINHO_LLM_CONTEXT_TOKENS` (tokens; 8192 when unset or not a positive integer, raised to 1024 when lower), counted at 4 characters a token: the budget is `floor(window × 0.8) × 4` characters (26,212 at the default) and never more than 32,000, because the prompt travels as one process argument. Human turns are now stored up to 8000 characters (was 1500; answers stay at 1500), and a turn past the 200-turn cap is folded into the summary instead of dropped. The summary is stored with the session (scrubbed) and reloaded after a restart, and a smaller window condenses further from it. When a session ends or idles out (also when that is found at load after a restart), its summary, last 20 turns, up to 100 answer message ids and its project are kept, scrubbed, in the new `conversation_threads` table (schema v13) for 30 days after its last activity, then purged (on every read and write of that table, hourly in the bridge and on each WATCH poll cycle). Within that time, the same user's reply to one of its answers, or their message in its thread (no @mention needed), passes the channel allowlist, actor / deny-list and mute / rate gates and starts a new session seeded with the summary and kept turns, in the conversation's project (a project that no longer resolves fails the worktree bind like any talk, never falling back to the default project); it works only in the same thread, or the same channel outside threads, a live session already carrying the conversation is continued instead, anyone else's reply or thread message never gets it, and a new @mention elsewhere in the channel still starts fresh. An Answer form submit (#294) is condensed like chat. - **Schedule ticks check the creator; the daemon ticks against the live allowlist** — [#236](https://github.com/CorvidLabs/Corvidinho/pull/236) (DISCORD-SCHEDULE-3, ALLOW-3, ALLOW-4, IDENTITY-2, CLI-8): a tick checked only the schedule's channel and then ran and posted as the creator, so a schedule whose creator was deny-listed, or missing from a non-empty user allowlist, still ran and posted while a live message from that user was refused. Each tick now runs the creator through the same actor gate as live Discord ingress (the configured owner passes, deny wins) and then the channel check, before any worktree or agent spawn and again right before the post. A run refused at start is recorded failed as `creator not allowlisted: …` (no user id in it) or `channel not allowlisted: <id>` and counts toward the 5-failure auto-pause; a creator refused mid-run gets no post. Schedules store no member roles, so with a non-empty role list a creator admitted only through a role is refused unless listed by user id or the owner; with empty user and role lists, ticks stay channel-gated as before. Mutes are not part of the tick gate. `corvidinho daemon` loaded the allowlist once at start, so after `/admin channels remove` or a users/deny edit it kept running the removed channel's schedules until restart, and it passed no owner to the scheduler; it now re-reads the allowlist (file, env overlays, `DISCORD_CHANNEL_IDS`) before every tick and passes the configured owner, loaded once at start. If the allowlist file cannot be read or parsed, the daemon skips that tick and logs `tick.allowlist_failed` with the loader's error (never list values): nothing runs and due schedules stay due.
- **Daemon schedule runs that need a human reach Discord** — [#238](https://github.com/CorvidLabs/Corvidinho/pull/238) (AUTONOMY-2, AUTONOMOUS-7, AUTONOMY-4, SAFE-8, DISCORD-SCHEDULE-3): when a schedule run claimed by `corvidinho daemon` stopped to ask (stuck, clarify or the daily spend cap), nothing was posted: the daemon has no Discord connection, the run row stored only `failed (exit 1)`, and the question was lost even with a bridge on the same data dir. The run row now records the ask (its reason and the question, secret-scrubbed and capped; schema **v11**), and the bridge's scheduler tick posts each schedule's newest pending ask to the schedule's channel once, with the same pings as a run the bridge ran itself: the owner for stuck and spend-cap, the schedule's creator for clarify, at most one ping per question and one per cap episode, no reply hint on a spend-cap ask, and a pending 80% spend warning attached. An ask is dropped once a later run of that schedule has finished or the schedule is deleted, and a schedule with no channel never gets its ask posted. Delivery is gated live like #236: while the creator or the channel is refused, the ask stays pending, and it is posted on the next tick after `/admin` allows them again (a bridge run refused at post time also leaves its ask pending). A post that returns false or throws hands the ask back for the next tick (a throw is logged as `[scheduler] ask failed: …`); the claim is a compare-and-set, so two bridges on one DB post it once. A tick never waits for these posts, and bridge stop waits up to 3 s for one in flight. The daemon itself still needs no Discord token, never posts, and logs `run.needs_human` (`reason` `stuck`, `clarify` or `spend-cap`); with only the daemon running, the question waits on the run row until a bridge starts.

### Agent verify gate and per-tier models

- **Verify runs whenever the git working tree changed, not only when a tool says so** — [#237](https://github.com/CorvidLabs/Corvidinho/pull/237) (AGENT-4, AGENT-4.a): the verify gate ran only when a tool reported changed files (`files-write`, `files-edit`, `files-delete`, `git-commit`), so an edit made through `shell-exec`, a commit made in a shell, a Fledge command or any other process in the checkout could end `done` with verify skipped. With the gate on, the loop now snapshots the git state after Planning (`HEAD`, `git status`, and a fingerprint of each already-dirty path) and, after each attempt, adds every path that differs (new commits, newly dirty or untracked files, deletions, already-dirty files whose content changed, dirty files that became clean) to `filesChanged`, up to 1000 per run, with one `Verify gate: the git working tree has N changed path(s) no tool reported (…)` note naming up to 5 of them. Verify then runs as usual, and a shell-only retry after a failed verify is verified again with the failure feedback. If git cannot read the diff after a good start snapshot, verify runs anyway (fail closed). A non-git cwd or an unreadable start snapshot keeps the old tool-reported behaviour; pre-run dirt the run leaves untouched, gitignored paths, and changes inside a nested repo or submodule are not counted; in a shared (non-worktree) checkout, another process's edits during the run count as this run's. `--no-verify` and `verify_before_complete = false` are unchanged and take no snapshot.
- **A model per capability tier** — [#234](https://github.com/CorvidLabs/Corvidinho/pull/234) (AGENT-5, SAFE-8): the tier already chose the tool catalog, but every tier called the one `CORVIDINHO_LLM_MODEL`, including read-tier delegate workers and council voices. New optional `CORVIDINHO_LLM_MODEL_READ`, `CORVIDINHO_LLM_MODEL_TOOL` and `CORVIDINHO_LLM_MODEL_CODE` set the model for runs at that tier (a blank value counts as unset), each falling back to `CORVIDINHO_LLM_MODEL` and then `gpt-4o-mini`; `--tier`, and a delegate or council child's own tier, now picks the model as well as the tools. Endpoint and API key stay shared across tiers. With no per-tier key set, nothing changes. SAFE-8 prices the model actually sent; an unpriced model's ask now names the key that set it (for example `CORVIDINHO_LLM_MODEL_READ`), and with a cap set, the doctor `spend` line and `/status` flag an unpriced per-tier model with its tier (`read-tier runs stop and ask`). The doctor `llm` line appends `; per tier: read …, tool …, code …` (model names only, never the key) when any per-tier key is set. `/status` and the Discord thinking footer still name the env tier's model, which is what bridge runs use.

### SpecSync

- **Local spec-check runs at CI strictness; `specsync score` report** — [#235](https://github.com/CorvidLabs/Corvidinho/pull/235) (SPECSYNC-2, SPECSYNC-3, SPECSYNC-6, SPECSYNC-7): the Fledge `spec-check` task ran plain `specsync check`, so the verify lane passed a tree that the CI Spec Sync Action (`require-coverage: "100"`) rejects, such as a new source file with no spec. `fledge.toml` now runs `specsync check --require-coverage 100` (no `--strict`, matching `strict: false` in `spec-sync.yml`), and a parity test fails if the two drift apart; a spec-check failure still goes through retry and ends with `verified=false`. `specsync-check` now uses the Fledge task only when fledge is on PATH and the project's own `fledge.toml` defines `spec-check` (a `fledge.toml` it cannot parse keeps the Fledge path); otherwise it runs the local `specsync check`, where before it failed with `Unknown task 'spec-check'` or `no fledge.toml found`. The new `specsync-score` tool (tier 0, not dangerous, refuses `--root`, forwards module names, `--explain` and `--format json`) and `corvidinho specsync score` run the local `specsync score` with no API key; before, a score report needed the dangerous `shell-exec`.

### Plugins and shell safety

- **node, python and cargo runner plugins** — [#241](https://github.com/CorvidLabs/Corvidinho/pull/241) (PLUGIN-4, PLUGIN-2, SAFE-1, SAFE-3): new `node-exec`, `python-exec` (runs `python3`, else `python`) and `cargo-exec` run that toolchain with the given argv exactly as given (no shell, no expansion), starting in the project root or task worktree. Each registers only when its binary resolves on an absolute PATH entry when the builtins load (a relative entry such as `.` is ignored, and Bun's own `node` shim does not count as node), so a missing toolchain is neither registered nor offered. `corvidinho plugins list` prints a `Language runners (PLUGIN-4): …` line naming what loaded and `<name> not loaded: <tool> not found on PATH` for each missing one, and still exits 0; `--json` just lists the loaded runners. Each is dangerous with `minTier` 2: denied in non-interactive runs unless named in `CORVIDINHO_ALLOWLIST`, and offered to the model only at code tier with dangerous tools included, to ADMIN. The child gets the verify lane's scrubbed env (no Discord config, GitHub tokens, audit key, acting identity or LLM keys, and no `CDPATH`/`OLDPWD`) plus `CORVIDINHO_PROJECT_ROOT`; output is secret-scrubbed and capped at 64 KiB per stream; the process tree is killed after 10 minutes (exit 124) or on the calling run's abort (exit 130); a binary that cannot start returns exit 127, and empty argv is a usage error (exit 1). The start dir is not a SAFE-3 clamp: code a runner runs can `chdir` elsewhere. `task run` does not offer dangerous tools to the model yet, so today the runners are reached through `corvidinho plugins run` and catalogs built with dangerous tools.
- **The shell `cd` clamp reads quoting the way the shell does** — [#226](https://github.com/CorvidLabs/Corvidinho/pull/226) (SAFE-3): the check that keeps `shell-exec` commands from `cd`-ing out of the project root could disagree with the shell about what was quoted and what was code, so a real `cd` ran outside the root while the check passed (an escaped backslash before a newline, a quote inside a `#` comment, a lone quote in a here-doc body, `)` in a comment inside `$( )`, a backtick in a here-doc delimiter, bash `$'…'` quoting, a shell's `-c` string). Backslash-newline continuations are now handled inside the tokenizer; `#` at a word start comments to the end of the line; a here-doc body is data up to the exact delimiter line (tabs stripped for `<<-`), while an unquoted body's `$( )` and backticks are still checked; the end of `$( )` comes from the same tokenizer. A command holding `$'` is also read the way bash reads ANSI-C quoting (so `cd $'\x2e\x2e'` refuses), a command holding `<<` is also read with every line as code, and the command refuses if any reading refuses. The `-c` string of a shell (`sh`, `bash`, `dash`, `zsh`, `ksh`, `mksh`, `ash`, `yash`, `posh`, by name or path, anywhere in the command, so `env`, `exec`, `nohup`, `timeout`, `xargs` and `find -exec` wrappers count) is checked like an `eval` argument. A `cd`/`pushd` left open by an unterminated quote or a trailing backslash refuses, and nesting deeper than 64 levels of `$( )` / `eval` / `-c` refuses as `(nested too deeply to check)` (before, about 20,000 nested `$(` threw `RangeError` out of `shell-exec`). Refusals are still exit 2 with the SAFE-3 message, before spawn. Still out of reach for this lexical check: other interpreters' `chdir` (`python3 -c`, `perl -e`, `node -e`), `sh script.sh`, `.` / `source`, and tools' own `-C dir` flags. Test-only: a `bun test` segfault on Bun 1.3.11 in the web-fetch TLS loopback test is worked around.

### Releases

- **Every package version gets a tag and a GitHub Release from CI** — [#231](https://github.com/CorvidLabs/Corvidinho/pull/231): the release workflow ran only on a hand-pushed `v*` tag, and agent sessions cannot push tags, so 0.0.12, 0.0.13, 0.0.16, 0.0.18, 0.0.21 and 0.0.23–0.0.29 had no tag and no Release. `.github/workflows/release.yml` now tags from CI with `GITHUB_TOKEN`: on a push to main it tags every release version that has no tag yet, oldest first, up to main's `package.json` version, each at the commit that bumped it, and creates its Release (the version's CHANGELOG section, the commits since the previous `vX.Y.Z` tag, and the updater line), so a release PR needs no hand-pushed tag and a cancelled or failed run is caught up by the next push. A hand-pushed `vX.Y.Z` tag still gets its Release (with a warning if its commit has a different `package.json` version or is not on main), and a manual `workflow_dispatch` run on main with `versions` tags and releases the listed versions. Existing tags and Releases are never moved, edited or deleted; the only edit is marking main's version Latest. GitHub starts no run when more than three tags are pushed at once, so use the manual run for bulk tags.

### Audit and agent loop

- **A keyed audit chain cannot be downgraded row by row** — [#209](https://github.com/CorvidLabs/Corvidinho/pull/209) (SAFE-5): with `CORVIDINHO_AUDIT_HMAC_KEY` set, an unkeyed row after a keyed row now reads as `chain BROKEN at #N` (a keyed row rewritten and relinked as plain SHA-256 used to pass as "mixed"), and a process without the key refuses to append after a keyed row, so it refuses dangerous plugin runs and `/admin` changes instead of breaking the chain. An unkeyed prefix followed by keyed rows (key set later) still verifies. Downgrading the whole keyed tail or truncating it is not caught; that needs an anchor outside the DB.
- **No more "database is locked" on audit writes** — [#211](https://github.com/CorvidLabs/Corvidinho/pull/211) (SAFE-5, SAFE-6): audit appends and the SAFE-6 re-scrub take the SQLite write lock up front, so while another process (bridge, daemon, watch, CLI) writes to the shared DB they wait under the busy timeout instead of failing at once. Before, a lost `started` row refused the dangerous run and a lost `ok`/`error` row left the audit trail without an outcome.
- **`task run` stops cleanly; a stalled LLM request times out** — [#207](https://github.com/CorvidLabs/Corvidinho/pull/207) (AGENT-3): on the first SIGINT/SIGTERM `corvidinho task run` cancels the run, prints the cancelled result, exits 130 and kills the whole `fledge lanes run verify` process tree (the lane used to keep running in the background). ### Live NDJSON event stream for bridges (#73) — [#139](https://github.com/CorvidLabs/Corvidinho/pull/139)

### ⚠ Upgrade notes

### Security — memory ACL hardening (#59 follow-up) — [#128](https://github.com/CorvidLabs/Corvidinho/pull/128)

- Memory plugins no longer accept `--user`, `--admin`, or `--db` from argv. In the LLM tool loop argv is model-controlled, so the model could previously read or overwrite any user's memories and self-assert ADMIN (MEMORY-ACL-1..4). The acting user and ADMIN now come only from bridge-set env (`CORVIDINHO_ACTING_DISCORD_USER_ID` / `CORVIDINHO_ACTING_IS_ADMIN`).
- ADMIN is re-checked in the plugin handler: the bridge's per-dispatch `CORVIDINHO_ACTING_IS_ADMIN=1` is required (scheduled runs never get ADMIN) and the live config must agree — empty `CORVIDINHO_DISCORD_ADMIN_USERS` + `_ROLES` ⇒ nobody; deny-listed/muted users are never ADMIN; admin user id, or admin roles configured (ADMIN-4). Superseded in this same package by owner-only ADMIN ([#141](https://github.com/CorvidLabs/Corvidinho/pull/141), upgrade note above): the live check now requires the configured owner, and no owner ⇒ nobody.
- `memory-forget` / `memory-override` are real two-phase (SAFE-4): run once for a confirm token (no content), then `--confirm TOKEN` from a new turn within 10 minutes. The token is HMAC-bound to op + actor + memory id + row state (+ override content) and is single-use. No schema change.
- `memory-recall --include-deleted` is ADMIN-only.
- Phase 2 also needs the token to appear in the human's own message (the bridge passes only human-typed tokens), so the model cannot confirm from its own memory.
- Discord / schedule / WATCH spawns run non-interactive (SAFE-1), and the tool loop only runs tools it offered this run — a dangerous plugin can no longer be called by name.
- Re-storing a memory key keeps the prior content as a soft-deleted row instead of overwriting it (no non-admin forget path).
- Discord spawns always overwrite the acting env; WATCH spawns clear it.
